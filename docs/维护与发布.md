# 维护与发布

面向维护者。描述发布拓扑、GitHub 驱动的新发布链路、两个服务器脚本的用法，以及数据边界与几条容易踩的规矩。文中一律用**变量名**，不写真实域名 / IP / 凭据；这些值由维护者在服务器上通过环境变量或配置文件提供。

---

## 1. 发布拓扑

```text
$DEPLOY_ROOT/                    发布根（例如运维自己选的一个绝对路径）
├─ source/                       Git 工作树（$SOURCE_DIR），只用来拉取和构建
├─ shared/data/                  首批数据的唯一持久副本（$SHARED_DATA_DIR）
├─ releases/<YYYYmmdd-HHMMSS>/   每次发布一个自包含目录（$RELEASES_DIR）
├─ current -> releases/<版本>     nginx root 指向它（$CURRENT_LINK），切软链就是切版本
├─ .staging/                     构建临时目录，trap 清理
├─ logs/deploy.log               发布摘要追加在这里
└─ acme/                         证书验证目录，绝对不要动
```

nginx 的站点 root 指向 `$CURRENT_LINK`（即 `$DEPLOY_ROOT/current`）。**旧 release 全部保留用于回滚，回滚只切软链，不删除任何文件。** `acme/` 与 `shared/data/` 同样绝不删。

---

## 2. 新发布链路（GitHub 驱动）

发布不再是「本机打包上传 → 服务器解包」，而是四步：

1. **本地提交推送 GitHub**：改仓库 → 功能分支 → 复核 → fast-forward `main` → 推送 `origin/main`。
2. **服务器拉取**：发布脚本在 `$SOURCE_DIR` 里 `git fetch --prune` 再 `git reset --hard origin/$BRANCH`。这一步只动 `$SOURCE_DIR`，**不碰 `current`**。
3. **服务器构建干净产物**：在 `$DEPLOY_ROOT/.staging/<时间戳>-<pid>` 里跑 `node "$SOURCE_DIR/tools/build.mjs" --out <staging>/site`。构建零依赖、纯字节拷贝，跳过 `dist/data/` 与 `dist/submissions/originals/`。
4. **原子切链 + 健康检查**：产物 `mv` 进 `releases/<名字>`，`ln -s` 出软链再 `mv -Tf` 原子覆盖 `current`，然后回读线上。

全程不经过手工整包上传，构建可复现、可审计。

## 3. 服务器脚本

### 3.1 环境变量

两个脚本都从环境变量读配置；可选由 `$DEPLOY_ENV` 指定一个配置文件加载。**环境变量优先于文件**：脚本会先记住已存在的环境变量，读完配置文件再覆盖回去。

| 变量 | 必填 | 默认 | 说明 |
|---|---:|---|---|
| `DEPLOY_ROOT` | 是 | — | 发布根目录 |
| `SOURCE_DIR` | 是 | — | Git 工作树目录 |
| `REPO_URL` | 是 | — | 公开仓库地址 |
| `BRANCH` | 是 | — | 发布分支，如 `main` |
| `HEALTH_URL` | 是 | — | 站点根 URL；**必须由外部提供**，脚本不内置域名 |
| `SHARED_DATA_DIR` | 否 | `$DEPLOY_ROOT/shared/data` | 首批数据持久副本 |
| `RELEASES_DIR` | 否 | `$DEPLOY_ROOT/releases` | release 目录 |
| `CURRENT_LINK` | 否 | `$DEPLOY_ROOT/current` | current 软链 |
| `DEPLOY_ENV` | 否 | — | 配置文件路径；未提供则只用环境变量 |

### 3.2 `ops/deploy-server.sh`

```bash
ops/deploy-server.sh
```

固定顺序执行，任一步失败都以非零退出并保持 `current` 不变或回滚：

1. 校验 5 个必填变量齐全，缺一个立即报错退出；
2. `flock -n` 拿 `$DEPLOY_ROOT/.deploy.lock`，拿不到直接退出（防并发发布）；
3. 工作树不存在则 `git clone`，存在则 `fetch --prune` + `reset --hard origin/$BRANCH`；打印将要发布的 commit SHA 与 subject；
4. 在 `$DEPLOY_ROOT/.staging/<时间戳>-<pid>` 里构建；构建失败就清理 staging 退出，不动 `current`；
5. **先**给产物设权限（目录 755、文件 644），**再** `cp -al "$SHARED_DATA_DIR"` 硬链接成产物里的 `data`；
6. 校验产物里 `index.html`、`data/blue-fish-classification.json`、`submissions/works.json` 存在；
7. `nginx -t`；
8. `mv` 产物进 `releases/<YYYYmmdd-HHMMSS>`（同名则追加 `-<pid>`），并记录旧 `current` 的目标；
9. 原子切链：`ln -s releases/<名字> current.new && mv -Tf current.new current`；
10. 健康检查：首页、`/robots.txt`、`/submissions/works.json` 三个 URL 必须 200；再从新 release 的 `submissions/previews/` 下 `find | sort | head -1` 稳定取一张 `.webp`，用它的相对路径回读，必须 200 且内容长度 > 0；另用 node 打印 `published` 记录数；
11. **任一健康检查失败：立刻用同样的原子方式把 `current` 指回旧目标**，打印失败原因，非零退出；
12. 成功则把旧 release、新 release、commit SHA、健康检查摘要追加到 `$DEPLOY_ROOT/logs/deploy.log`。staging 目录由 `trap` 清理。

脚本幂等：重复执行只是再从 `origin/$BRANCH` 构建一份新 release 并切链，不会覆盖或删除任何已有 release。

### 3.3 `ops/rollback-server.sh`

```bash
ops/rollback-server.sh <release目录名>
```

必须显式给出 `releases/` 下的目录名，**没有默认值**。流程：加载同样的配置 → 校验 `releases/<名字>/index.html` 存在 → 原子切链到该 release → 同样的健康检查 → 失败则指回原目标并非零退出。**不重新构建、不删除任何文件。**

### 3.4 失败与回滚行为

- 构建失败 / `nginx -t` 失败：`current` 不动（此时还没切链），staging 被清理；
- 切链后健康检查失败：`current` 原子指回旧目标；
- 首次发布（原本没有 `current`）失败：移除刚建出的 `current` 软链；
- 任何情况下都不删 release、不删 `shared/data`、不删 `acme`。

### 3.5 构建标记 `.build-output` 与 `--force-clean`

`tools/build.mjs` 在校验全部通过后，会在产物根写一个小标记文件 `.build-output`（内容固定一行、无时间戳，构建保持确定性），用途是让下次本地构建能认出「这确实是本脚本的产物」，从而安全地清空重建。

- 重复构建到同一个 `--out` 目录：因为标记在，可以直接清理重建；
- 指向一个已存在、非空、**又没有该标记**的目录时：构建会拒绝清空并给出提示，确认要删需显式加 `--force-clean`；
- 危险路径（文件系统根、系统目录、Git 安装目录、用户主目录等）即使加 `--force-clean` 也一律拒绝，绝不删除。
- 该标记只用于本地识别，**不随发布产物上线**：`ops/deploy-server.sh` 在 `chmod` 之后、`cp -al` 之前会 `rm -f` 掉它（删除必须发生在 `cp -al` 之前，之后不能再改动产物）。

## 4. 数据边界

| 数据 | 权威位置 | 进 git？ | 进发布产物？ | 说明 |
|---|---|---:|---:|---|
| 前端源码 `dist/`（`index.html` / `app.js` / `styles.css` / `tokens.css` / `robots.txt` 等）| 仓库 `dist/` | 是 | 是 | `dist/` 是站点根，也是前端权威源码 |
| 首批清单与预览 `dist/data/` | 服务器 `$SHARED_DATA_DIR` | **否** | 硬链接进每个新 release | 由仓库外的导入流程生成；不进公开仓库，也不再每版单独存一份 |
| 投稿原图 `dist/submissions/originals/` | 仓库 | 是 | **否** | 进 GitHub 供 Raw 下载，发布产物不含它 |
| 投稿派生图 `dist/submissions/previews/`、`dist/submissions/large/` | 仓库 | 是 | 是 | 随仓库入库 |
| 站长自用 `dist/owner-picks/` | 仓库 | 是 | 是 | 清单与原图都在本仓库 |
| 站点头像 `dist/avatar.png` | 仓库 | 是 | 是 | 随仓库入库 |

要点：

- `dist/` 是权威源码输入；服务器构建**只读仓库**，不再从上一版 release 里凑数据。
- `dist/data/` 不入库，由服务器 `$SHARED_DATA_DIR` 持久保存并硬链接进每个新 release。
- 派生图（`previews/` / `large/` / `avatar.png`）随仓库入库，所以**服务器构建不需要 Pillow**——图片处理在维护者本地用 `tools/generate_image_derivatives.py` 完成后再提交。

### 为什么硬链接数据要在 chmod 之后做

`cp -al` 建的是**硬链接**：新 release 里的 `data/*` 和 `$SHARED_DATA_DIR`、以及所有旧 release 里的同名文件**共享同一个 inode**。inode 上也带着权限位。所以如果顺序反了——先 `cp -al` 再 `chmod -R`——`chmod` 会顺着硬链接把共享数据和所有旧 release 里同一 inode 的权限一起改掉。

发布脚本因此固定为「**先 chmod 产物，后 cp -al data**」。此时产物里还没有 `data`，`chmod` 碰不到硬链接。

## 5. 旧上传包清理原则

服务器 `$DEPLOY_ROOT` 根目录下可能留着历史手工上传的 `*.tgz`。它们**不是 release**，只是旧发布方式（本机打包 → 上传 → 解包）的残留。

清理原则：

1. 只动根目录里命名形如 `<时间戳>.tgz` 的文件，别的一概不碰；
2. 删之前先核实它没有被 nginx 配置、cron、systemd unit 或 `current` 引用；
3. **必须等新流程发布的 release 健康检查通过之后**才删；
4. 绝不删任何 release、绝不删 `shared/data`、绝不删 `acme`。

---

## 6. `?v=` 缓存规则

改了 `dist/app.js` / `dist/styles.css` / `dist/tokens.css`，**必须同步 bump `dist/index.html` 里的 `?v=` 数字**（当前 `tokens.css?v=13`、`styles.css?v=17`、`app.js?v=19`）。

理由与现状：文本资源目前的响应头是 `Cache-Control: no-cache`，浏览器每次仍会带 `If-None-Match` 回源做协商缓存校验。**`?v=` 现在主要起到「换一个 URL」的作用**，让新版本绕过旧的缓存条目——不 bump 的话，访问者可能继续拿旧内容，容易误判「修复没生效」。想真正靠它拿到长缓存，还得同时调整 nginx 的 `Cache-Control`。
